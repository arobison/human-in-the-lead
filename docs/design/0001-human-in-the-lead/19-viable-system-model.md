# 19. Viable system model check

[Back to the index](../0001-human-in-the-lead.md)

Stafford Beer's viable system model says that any system able to keep itself going in a changing environment has five functions, plus an audit channel and an alarm channel. Missing any one is a predictable failure. This part uses the model as a **completeness check** on the design, not as an organizing principle: each function should be present, named and owned.

## 19.1 The check

| Function | What it does in Beer's model | Here | Owner | Where specified |
|---|---|---|---|---|
| **System 1: operations** | The units that do the primary work | Executors (tiers 0–3), each on one item in one worktree; the triager, reproducer, shaper, researcher, liaison and curator; the maintenance loop's upgrade work; docs updated as part of finishing work; the generalizer agent that drafts public feedback ([18.4](18-self-improvement.md#184-giving-feedback)) | Orchestrator dispatches; executors do | [Parts 2](02-loops.md), [5](05-execution.md) |
| **System 2: coordination** | Dampens oscillation between operational units so they do not collide | Claims in the branch's first commit; `touches` and serial-resource locks; port and worktree leases from the environment manager; the machine-wide registry of live executors, resource capacities and quiet holds ([13.4](13-operations.md#134-settings-in-four-layers)); the merge queue's dependency order and conflict handling; ID allocation; the one-orchestrator lease; the scheduler's idempotent jobs; stability rules for controllers | Orchestrator, scripts | [Parts 3](03-data-model.md#claims-and-closing), [11](11-metrics-and-control.md#stability-rules), [13](13-operations.md), [14](14-integration.md) |

## 19.2 The 3–4 balance

Beer's central warning is that System 3 (run today well) and System 4 (prepare for tomorrow) compete for the same resources, and System 5 must arbitrate. Unbalanced, a system either optimizes itself into irrelevance (3 dominates) or plans without delivering (4 dominates).

Loops are nested by speed ([part 2](02-loops.md#loops-nested-by-speed)): the slowest, strategy, is System 5 acting on System 4's evidence; slow loops set the setpoints of medium and fast ones. Here the arbitration is explicit: the owner's **portfolio weights** and **target shares** ([part 2](02-loops.md#24-prioritization)) set how much of the token budget goes to research, shaping and learning against delivery, and the prioritization rule enforces the shares within tolerance. The shaping loop's own controller (pause shaping when shaped projects pile up unbet) stops System 4 from outrunning System 5's capacity to decide.

## 19.3 Recursion

Beer's model is recursive: each System 1 unit is itself a viable system. Here, a tier-3 session working on a large item is a small orchestrator in its own right: it may dispatch its own background agents for parts of its item, keep its own question protocol, and report up in the fixed shape. The same rules apply at that level (report shape, decision rights), with the parent orchestrator as its System 3 and the owner still as System 5. The recursion stops short of the shared state, to keep one writer: a tier-3 session's sub-agents work inside its worktree and branch, never on `main`; it never writes the ledger or allocates IDs; and it reports its sub-agents' usage in its own report, which the orchestrator records. Questions that are the owner's go up, not sideways.

**One level up: the person.** Settings in four layers ([13.4](13-operations.md#134-settings-in-four-layers)) add a level above projects: one person runs several projects on the same machines and accounts. Each project is then a System 1 unit of that larger system. This is the level where projects could starve each other, so each function has a home there:

| Function | At the person level |
|---|---|
| System 2 | The machine registry of live executors, resource capacities, quiet holds, and the merge lock per repository |
| System 3 | Shares between projects near the reserve; the strictest-layer caps on executors and budgets |
| System 5 | The person file: the person's plans, limits, appetite for parallel agents and shares |

## 19.4 Gaps the check found

Applying the check while drafting surfaced these needs, each now addressed:

- **No audit separate from the units' own reports** (System 3\*). Addressed by making the author unable to supply its own acceptance evidence, and by random human-read samples.
- **No alarm path** around quiet hours and digests. Addressed by the sev-1 page.
- **System 5 overloaded by System 3 traffic** (every operational question reaching the owner). Addressed by decision rights, logged calls and precedent: the owner sees operational detail only as digests, and decides only what is novel or theirs. Two rules protect System 5 further. Two-way doors default to action ([part 4](04-decision-rights.md)). When the decision budget is full, only easy-to-undo calls take their recommendation, and each is listed in the digest ([part 2](02-loops.md#the-owners-attention-as-a-budget)).
- **System 5's own quality was never measured.** Beer gives System 5 no audit. Part 23 adds one: a judgment record per person, matched to outcomes, and a calibration review that each person sees privately ([part 23](23-people-in-the-lead.md)).
- **Milestones and releases had no place** in the check. Milestones now sit in System 4, their independent checks in System 3\*, and release commitments in System 5.

Remaining weaknesses, carried as risks:

- **System 2 across machines** is weaker than within one: claims on the second machine are invisible until its bundle is fetched, so two machines can start the same item. The reserved ID blocks prevent ID collisions, not duplicate work. Mitigation: the orchestrator assigns items to the second machine on `main` (the claim block's `host` field) and ships the assignment in the next bundle before that machine starts them; the second machine works only on items assigned to it.
- **System 4's view of users** depends on intake sources the project has; a project with no public channel has a narrow window. Research briefs for the owner are the mitigation.
