## Done when

- A measurement over the last merged pull requests records, for each, how many passes and check rounds it took after it was approved, and which files caused the conflicts or the main-merge rounds (the plugin mirrors, the design error table, skill text and views are the suspects); the figures are in the item, not guessed.
- From the measurement, a proposal names the cause that costs the most and its fix, for the owner to choose: a merge train that tests the waiting branches together (the queue already builds batches), generated mirrors regenerated by the queue instead of committed in every feature pull request, or shared text moved out of the files every item edits. No fix is built before the owner picks one.
- `npm run check`, the offline eval gate and `hitld work check` pass.
- The measurement separates the rounds caused by a main move that changed only files a check does not read (work items, for one) from the rounds caused by shared files the branches both edit. A passing result is reused only where each check's inputs are declared and none changed: `work/` files are an input to the full `check` job today (it runs `hitld work check`), so a work-only main move does not by itself make a rerun pointless; the proposal says which checks could be reused and which cannot.

## Why

GitHub issue 677: items finish on their branches far faster than they reach main; each merge moves main, so every other waiting branch needs a main-merge and a full round of checks again, mostly from conflicts in shared files that every item updates. On 2026-11-25 pull request 658 took two passes and two check rounds after the owner's approval, and so did 676. A limit on starts only hides the queue; this is what makes it slow.
